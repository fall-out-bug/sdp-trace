# Block 27 Observability Telemetry Fixtures

This directory is a downstream-consumer fixture for Block 27 standard telemetry
export. It is not a product dependency, dashboard package, alert policy, or
gate.

The intended product boundary is:

```text
sdp-trace cross-repo posture JSON -> Prometheus text metrics -> downstream consumer
```

`sdp-trace` owns the factual telemetry export. Prometheus, dashboards, alerts,
reports, paging, and risk decisions remain downstream responsibilities.

## Expected Export

When the Block 27 CLI lands, regenerate the Prometheus text snapshot from the
Block 21 posture fixture:

```bash
sdp-trace export telemetry \
  --profile prometheus-text-v1 \
  --cross-repo-posture examples/block21-cross-repo-posture/valid-movement/cross-repo-posture-export.json \
  --out examples/block27-observability-telemetry/prometheus/metrics.prom
```

For textfile collector handoff, write to a collector directory instead:

```bash
sdp-trace export telemetry \
  --profile prometheus-text-v1 \
  --cross-repo-posture examples/block21-cross-repo-posture/valid-movement/cross-repo-posture-export.json \
  --out /var/lib/node_exporter/textfile_collector/sdp_trace_posture.prom
```

`prometheus/metrics.prom` is checked in as a regression fixture generated by the
live exporter. It is not authority by itself. The CLI test regenerates the output
from the Block 21 fixture and fails if the committed snapshot drifts.

## Downstream Prometheus Fixture

`prometheus/prometheus.yml` is a minimal Prometheus scrape example for a local
node exporter textfile collector. It assumes a separate process serves the
generated `.prom` file as metrics at `localhost:9100`.

This fixture deliberately does not include:

- Grafana dashboards;
- Alertmanager rules;
- Telegram, Slack, or paging routes;
- risk thresholds, health scores, colors, or gate decisions.

Those consumers may use the exported metrics, but they are outside the
`sdp-trace` product boundary.

## Verification Notes

After the exporter exists, the integration check should verify:

- the committed `metrics.prom` is regenerated from the live Block 21 fixture;
- the regenerated file is byte-for-byte stable;
- `not_assessed`, `cannot_verify`, untrusted input, and refusal facts remain
  visible when their labels are safe;
- unsafe label values fail closed without partial metrics output.
