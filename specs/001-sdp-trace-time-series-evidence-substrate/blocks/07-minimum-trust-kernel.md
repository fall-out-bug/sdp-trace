# Block 07: Minimum Trust Kernel and Canonical Proof Authority

Status: implementation in progress; Slice 0 implemented under verifier authority; Block 07 not closed
Parent Spec: `001-sdp-trace-time-series-evidence-substrate`
Audience: technical executive, CIO, CISO, release owners, future external policy consumers

## Purpose

Block 07 responds to the product objection:

> Why should a technical executive or CISO trust a product that says real trust will arrive later?

The answer cannot be more prose. `sdp-trace` must make its own claims verifier-derived before it asks customers to rely on those claims.

Block 07 defines the Minimum Trust Kernel: the smallest contract, verifier, and evidence loop that prevents the repository from saying "verified", "complete", "trusted", or "production release verified" unless the selected verifier profile supports that exact claim.

## Problem Statement

The current tree contains contradictory evidence:

- Block 04 records implementation and pi review closure, while current validation fails.
- T070 says validation was verified, while `npm run validate` and `scripts/verify-self-attestation.sh --all` fail.
- The release verification example records matched artifact digests while manifest verification reports digest mismatches.
- The Block 06 report overclaims observed proof states while `proof-states.json` records `completion_state: incomplete`.

This is a trust failure, not stale bookkeeping. If prose, task checkboxes, matrices, and machine proof can disagree, the repository is vulnerable to false evidence.

## Product Boundary

`sdp-trace` records and verifies evidence-backed claims. It does not accept risk, decide readiness, decide degradation, or produce policy verdicts.

However, `sdp-trace` owns the integrity of its own claim surface. A downstream consumer must be able to reject a false `sdp-trace` claim without reading prose.

## Trust Anchor Assumption

The Minimum Trust Kernel verifies artifacts within a selected checkout or source subject. It does not magically prove that the checkout itself is benevolent.

The bootstrap assumption is explicit:

- A verifier run trusts the gate set present at the selected source subject unless an external production trust profile is selected.
- Consumers who distrust the selected source subject must verify the checkout out of band, such as a signed git commit, protected CI ref, vendor release channel, signed source archive, or customer-controlled source snapshot.
- `gate_set_subject` binds the proof to the verifier scripts, schemas, and gate definitions that ran. It does not by itself defeat an attacker who can modify the verifier and the proof in the same untrusted checkout.
- External production trust is the profile that adds a signer identity, protected release channel, and transparency or audit anchor.

This is a product constraint: the kernel can make false claims detectable inside a trusted checkout. It cannot replace source distribution trust.

## Claim Authority Rules

1. Live execution of the canonical verifier is the claim authority.
2. A persisted `proof-summary` is an audit artifact or cache. It is untrusted until re-verified by the live verifier or signed under an external trust profile.
3. `proof-summary.schema.json` defines output shape, not truth.
4. `contract-release-verification` artifacts are subordinate views. They must either be generated by the verifier or reference the proof summary and gate set that derived them.
5. Reports, matrices, task checkboxes, review ledgers, and Beads mirrors are indexes. They cannot override verifier output.
6. SpecKit is the repository source of planning truth. Beads mirrors SpecKit execution state; when they disagree, SpecKit plus verifier output wins.
7. Validation has veto power: if the documented verifier fails, any closure claim depending on that verifier is false.
8. Digest claims must name their canonical subjects and scope.
9. Trust claims must be verifier-derived, not authored into JSON by hand.

## State Vocabulary

Every verifier state has a selected profile, subject, method, result, and reason when the result is not `pass`.

| State | Meaning | Required-state effect |
| --- | --- | --- |
| `pass` | The verifier ran the required check against named subjects and evidence supports the claim. | Satisfies the state. |
| `fail` | The verifier ran the check and evidence is missing, mismatched, invalid, expired, stale, unauthorized, or contradictory. | Fails the profile. |
| `not_assessed` | The verifier did not assess the state because it is outside the selected profile or intentionally absent from this profile. Under `source_bound_local_release`, `not_assessed` for `external_attestation_present` means external trust is out of scope for that profile; it does not mean external evidence exists. | Fails the profile if the state is required; allowed only for optional states. |
| `cannot_verify` | A required check could not run because required tooling, config, source access, or environment was unavailable. | Fails closed with a distinct exit code. |
| `incomplete` | A package or slice is honest but lacks required completion states. | Allowed for package-shape validation; fails completed-proof validation. |

`assessed` means the verifier executed the named method against the named subject and recorded `pass`, `fail`, or `cannot_verify`. Presence checks alone are insufficient unless the profile explicitly names presence as the method.

Every `fail`, `not_assessed`, `cannot_verify`, or `incomplete` state must include a machine-readable reason and, where useful, `next_required_evidence`.

## Proof Profiles

Block 07 uses proof profiles instead of maturity levels. A profile names the exact claim being made and the states required for that claim.

### `repo_baseline`

The repository's portable contract baseline is structurally honest and claim-consistent for this checkout.

Required states:

| State | Required method |
| --- | --- |
| `schema_json_valid` | Parse all schema JSON. |
| `committed_examples_parse` | Parse committed JSON examples. |
| `portable_schema_examples_valid` | Validate portable schema/example pairs. |
| `negative_fixtures_rejected` | Execute negative fixtures and confirm expected failures. |
| `self_trace_package_valid` | Validate the self-trace package shape and references. |
| `artifact_safety_valid` | Run committed artifact safety checks. |
| `claim_tags_consistent` | Validate machine-readable claim tags in docs/tasks/matrices against verifier claims. |

Optional or forbidden states:

| State | Rule |
| --- | --- |
| `external_attestation_present` | May be `not_assessed` because this profile does not require external trust. Absence must be visible and must not imply production trust. |
| `production_release_verified` | Forbidden as `true`. It may be absent or `not_assessed` only. |
- `observed_slice_complete`

Explicitly excluded:

- production trust
- customer pilot readiness
- broad harness/model compatibility

### `source_bound_local_release`

The contract release candidate is bound to an immutable source subject and local release proof.

Required states:

| State | Required method |
| --- | --- |
| `repo_baseline` | `repo_baseline` profile passes. |
| `manifest_digest_verified` | Compute and compare the manifest digest. |
| `artifact_subject_verified` | Compute every selected artifact digest using declared normalization rules. |
| `source_subject_verified` | Verify that the selected source subject contains every required manifest subject. |
| `local_envelope_verified` | Verify that DSSE or local release envelope binds the manifest digest. |
| `local_identity_policy_matched` | Verify the local profile signer identity policy. |
| `freshness_verified` | Apply the manifest freshness policy against the configured reference time. |
| `rollback_checked` | Record rollback state for the selected local mechanism. |

Optional states:

- `external_attestation_present`
- `production_release_verified`

Forbidden:

- `trusted_contract_release: true`
- `production_release_verified.value: true`
- any wording that treats local DSSE or local private key possession as external trust

### `external_production_trust`

The release is externally trusted under a named profile.

Required states:

| State | Required method |
| --- | --- |
| `source_bound_local_release` | `source_bound_local_release` profile passes. |
| `external_trust_profile_selected` | Match one supported external profile. |
| `external_attestation_present` | Verify Sigstore/Rekor evidence or a named customer PKI profile. |
| `external_identity_policy_matched` | Verify signer identity, source URI, protected ref or release channel, workflow identity, release captain, and approval refs. |
| `transparency_or_audit_verified` | Verify the signing event or release artifact against Rekor inclusion, customer audit log, timestamp authority, or named equivalent. |
| `production_release_verified` | Derive `production_release_verified.value: true` only after all production states pass. |
| `trusted_contract_release` | Derive `trusted_contract_release: true` from the same successful production state set. |

Optional states: none.

Missing external trust evidence fails this profile. It may be reported as `not_assessed` only when another profile, such as `repo_baseline` or `source_bound_local_release`, is selected.

Supported external profile taxonomy:

- `sigstore-rekor-keyless-v1`: DSSE over an in-toto statement, OIDC identity, protected ref or tag, workflow identity, approval refs, Rekor inclusion proof, freshness, and rollback policy.
- `customer-pki-audit-v1`: customer-named certificate or public key identity, accepted trust root, protected release channel, release captain, approval refs, timestamp or append-only audit evidence, freshness, and rollback policy.

`private-equivalent` is not an evidence type. It is invalid unless it maps to a named profile with required evidence.

### `observed_slice`

A specific harness/model/stack slice has observed evidence.

Required states:

| State | Required method |
| --- | --- |
| `proof_context_ref` | Reference the proof summary context and source subject used by the slice. |
| `slice_id` | Hash or stable ID over adapter, harness, model, provider, stack, source, target, prompt, and package version. |
| `adapter_identity_observed` | Record adapter identity and version. |
| `harness_identity_observed` | Record harness identity. |
| `model_identity_observed` | Record requested and observed model identity. |
| `source_subject_recorded` | Record source identity. |
| `target_scope_recorded` | Record target scope. |
| `command_summary_recorded` | Record command summary without secrets. |
| `artifact_refs_recorded` | Record produced artifact references. |
| `export_limitations_recorded` | Record missing export/log limitations. |
| `redaction_safety_valid` | Validate redaction and safety evidence. |
| `package_state_valid` | Validate package state as `complete` or honest `incomplete`. |

An observed slice does not establish repo trust, production trust, broad compatibility, support, readiness, or policy pass/fail.

## Canonical Subjects

Every digest or match claim must name the subject it compares.

`source_subject` must use one of these forms:

- `git_commit_v1`: repository identifier when available, 40-character commit, optional tree digest, path set, and ref resolution evidence.
- `directory_snapshot_v1`: canonical directory snapshot digest, path set, normalization rules, producer, and generation time.
- `signed_source_archive_v1`: archive digest, signature or checksum evidence, path set, normalization rules, producer, and source channel.

`artifact_subject` is an ordered manifest artifact set with path, digest algorithm, digest, and normalization rules.

`proof_subject` is the proof artifact or envelope subject, such as a manifest digest bound by DSSE or an in-toto statement.

`gate_set_subject` is the verifier script, schema, and gate definition set that produced the proof summary.

`spec_subject` is the source-of-truth spec artifact set, including spec path, version, source subject, and digest. Rollback checks must bind to `spec_subject`, not just a version string.

`matched` is invalid unless both compared subjects, both digests, digest algorithms, and normalization rules are present.

## Verifier UX

The default command must answer: "Is the repository baseline honest from this checkout?"

It must not fail the baseline because an optional external tool slice is incomplete. Slice verification uses a separate command surface.

Recommended commands:

- `npm run verify`
- `npm run verify:baseline`
- `npm run verify:source-bound`
- `npm run verify:external-trust`
- `npm run verify:slice -- --slice opencode-minimax-kotlin-bazel`

Exit behavior:

- `0`: selected profile passes; optional `not_assessed` states may be present
- `1`: selected profile fails because required evidence is missing, mismatched, stale, invalid, unauthorized, contradictory, or false
- `2`: usage error
- `3`: cannot verify because a required check could not run

Missing dependencies for required checks fail closed as `cannot_verify`. Missing evidence for optional states is recorded as `not_assessed` and does not change exit code `0`.

## Claim Tags

The verifier must not rely on NLP over prose.

Any document, matrix, task, or report that intends to make an authoritative claim must include a machine-readable claim tag. Example:

```markdown
<!-- sdp-trace-claim: claim=trust_not_assessed; subject=trusted_contract_release; state=not_assessed; profile=source_bound_local_release; evidence=state:claim_tags_consistent -->
```

The claim-consistency check validates tags against proof summary output. Untagged prose is commentary and must not be treated as authoritative evidence. Docs may still be reviewed for misleading language, but that review is not the machine claim authority.

## Review Ledger Lifecycle

The Block 07 review ledger is a pre-implementation artifact, not a final implementation slice.

Required fields:

- `finding_id`
- `source`
- `severity`
- `target`
- `finding`
- `disposition`
- `spec_or_plan_change`
- `closure_state`

The first ledger may be Markdown for human review. Implementation must later add `schema/review-ledger.schema.json` and make future ledgers machine-checkable.

## Security Requirements

- A checked-in proof summary or release verification JSON is untrusted input unless re-verified by the canonical verifier or signed under an external trust profile.
- `production_release_verified.value: true` is invalid unless every required production state passes.
- `production_release_verified.value: true` is invalid under `source_bound_local_release`; it is valid only under `external_production_trust` after all required production states pass.
- `trusted_contract_release: true` is derived only from the same successful production state set.
- Every `missing`, `mismatch`, `invalid`, `expired`, `not_assessed`, `cannot_verify`, `incomplete`, or contradictory state must include a machine-readable reason.
- Dirty working tree, mutable source refs, stale manifest, missing artifact, digest mismatch, wrong signer, wrong identity policy, expired freshness, missing external evidence, and rollback suspicion fail closed for the profile that requires them.
- Rollback protection must bind proof summary to source subject, spec subject, gate set subject, proof generation time, and external transparency or audit evidence for production trust.
- Evidence and provenance cross references must be verified by tooling, not left to JSON Schema alone.

## Out of Scope

- Implementing external policy consumer policy thresholds.
- Claiming pilot readiness.
- Claiming broad harness/model compatibility.
- Making OpenCode, MiniMax, Kotlin, Bazel, Bazelisk, GitHub, or any provider SDK a product dependency.
- Treating a large all-repo manifest as the first kernel subject. The kernel should prove the smallest contract set needed for downstream consumers first.

## Non-Deferrable Trust Work

Verification of the selected external trust profile is not deferred work.

Block 07 may implement only one external profile first, but it must actually verify that profile for this repository before any customer-facing self-trust claim is allowed. If no real Sigstore/Rekor or named customer PKI/audit evidence is available, the correct state is not "implemented with deferred external trust"; it is "Block 07 open: external production trust evidence missing."

Automation convenience may be staged. The trust check itself may not.

## Acceptance Criteria

Block 07 spec is accepted when:

- Review findings from independent reviewers are recorded in a committed review ledger.
- The spec defines proof profiles instead of maturity levels.
- The spec makes live verifier execution the claim authority.
- The spec treats persisted proof summaries as untrusted audit artifacts unless re-verified or externally signed.
- The spec subordinates `contract-release-verification` to proof summary/verifier output.
- The spec defines state semantics and required/optional state tables.
- The spec forbids hidden production trust claims outside `trusted_contract_release`.
- The spec separates baseline validation from optional pilot slice completion.
- The spec requires external trust evidence before customer-facing trust claims.
- The implementation plan is split into reviewable chunks and no implementation starts before the spec review ledger is accepted.

Implementation is accepted only when:

- The current false closure claims are frozen or corrected by verifier-derived evidence.
- `repo_baseline` validation passes from the current checkout.
- Source-bound and external-trust profiles report precise `pass`, `fail`, `not_assessed`, or `cannot_verify` states.
- At least one supported external profile is exercised against real repository release evidence, or Block 07 remains open with `external_production_trust` failed or `cannot_verify`.
- A forged or stale trusted-release claim fails without relying on prose review.
- Block 06 incomplete packages can validate as honest incomplete packages but cannot support completed proof claims.
