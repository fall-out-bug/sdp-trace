# Block 07 Minimum Trust Kernel Implementation Plan

Status: implementation in progress; Slice 0 implemented and reviewed; Block 07 not closed
Parent: `07-minimum-trust-kernel.md`

## Goal

Make `sdp-trace` verifier-derived: the repository baseline can pass honestly, optional incomplete slices remain explicit, and trusted release claims cannot be authored without matching proof states.

## Execution Rules

- No implementation starts before the Block 07 review ledger records independent review findings and closes critical/major spec-gate findings.
- Each implementation slice gets review before the next slice starts.
- Workers must use minimal context and disjoint write scopes where possible.
- When write scopes overlap, frozen claims must not be modified unless a corresponding verifier state or review-ledger entry explains the transition.
- Machine proof wins over prose, tasks, and Beads mirrors.
- Beads mirrors SpecKit execution state; SpecKit plus verifier output wins on conflict.
- Hand-editing trust-result JSON to make proof pass is forbidden. Trust-result artifacts are regenerated, deleted, or explicitly marked stale by a verifier-supported state.

## Slice 1: Claim Tags and Claim-Consistency Baseline

Purpose: make doc/task/matrix claims mechanically checkable without NLP.

Files:

- create or extend `scripts/validate-claim-consistency.mjs`
- update `scripts/verify.sh`
- update claim-authoring docs
- add claim tags to docs/tasks/reports that make authoritative claims

Required behavior:

- authoritative claims use machine-readable claim tags.
- untagged prose is commentary and cannot close evidence.
- claim tags are checked against live verifier output.
- task closure claims naming commands are checked against current command results or marked stale.
- every claim-consistency implementation artifact is represented in the self-trace graph with evidence and provenance refs.

Claim tag grammar:

```ebnf
claim_tag = "<!-- sdp-trace-claim:" fields "-->"
fields    = field (";" field)*
field     = key "=" value
key       = "claim" | "subject" | "state" | "profile" | "evidence"
value     = token | quoted
```

Slice 1 allowed values:

- `claim`: `task_closed`, `command_verified`, `profile_passed`, `trust_not_assessed`
- `state`: `pass`, `fail`, `not_assessed`, `stale`, `cannot_verify`
- `profile`: `repo_baseline`, `source_bound_local_release`, `external_production_trust`, `observed_slice`
- `evidence`: `command_set:block04-t070` or `state:claim_tags_consistent`

Slice 1 command replay is intentionally narrow: only `command_set:block04-t070` is executable. A `state=pass` tag with that evidence fails unless every command in the set passes in the current checkout. A stale or not-assessed tag records the contradiction without replaying command evidence.

Slice 1 deliberately rejects arbitrary `state:*`, `proof:*`, and `none` evidence because those would look like proof without cross-reference verification. Broader evidence references move to Slice 5.

Review gate:

- A fixture or edited doc containing an unsupported authoritative claim tag fails with exit `1` and a named reason.
- Quoted criticism or non-authoritative prose does not fail by keyword alone.
- T070 is tagged as stale until the verifier can prove the named closure commands pass.
- `claim_tags_consistent` is `pass` only when the validator has checked all committed authoritative tags.

Implementation state:

- Implemented in `scripts/validate-claim-consistency.mjs`, `scripts/verify.sh`, `scripts/test-verify.sh`, `docs/claim-authoring.md`, and `specs/001-sdp-trace-time-series-evidence-substrate/tasks.md`.
- Covered by self-trace nodes, evidence, provenance, observation, and accountability entries under `examples/self-trace/`.
- `claim_tags_consistent` now passes for the committed authoritative tag surface.
- T070 remains tagged `state=stale`; it is not repaired or re-closed by Slice 1.
- Arbitrary `state:*`, `proof:*`, and `none` evidence are rejected until Slice 5 can verify cross-references.

## Slice 2: Freeze and Repair Current False Closure Claims

Purpose: stop the repository from presenting broken proof as closed proof.

Files:

- `specs/001-sdp-trace-time-series-evidence-substrate/tasks.md`
- `specs/001-sdp-trace-time-series-evidence-substrate/blocks/04-release-finalization-external-trust.md`
- retired research artifact
- `examples/contract-foundation/contract-release-verification.example.json`
- `examples/self-trace/self-attestation-verification.json`

Required behavior:

- T070 cannot remain a current verified claim unless the named commands pass.
- T070 must be recorded as stale and contradicting current verifier output, or repaired under verifier authority. It may not remain "verified" in any authoritative doc while current validation fails.
- Block 04 delivery state cannot claim current validation success unless the verifier supports it.
- Block 06 report must match `completion_state: incomplete` until completed proof states pass.
- `artifact_digest_status` must name its subject scope or be downgraded.
- self-attestation expectations must match current verifier-derived proof state or be regenerated by the verifier.
- Every committed JSON artifact that could be mistaken for a trust result, including contract release verification and self-attestation verification artifacts, must be regenerated from current verifier output, removed from the trust-result path, or labeled as untrusted shape/example output that must be re-verified before use.

Review gate:

- `npm run verify:baseline` fails if a current closure claim contradicts verifier output.
- `npm run verify:baseline` fails if any authoritative doc still claims "verified" for T070 while current validation fails.
- trust-result JSON without regeneration evidence or an explicit untrusted/example label fails claim consistency.
- No trust-result JSON is hand-edited into a passing state.

Implementation state:

- T070 is reopened as stale historical closure in `tasks.md`.
- Block 04 delivery state no longer claims current validation closure.
- Block 06 report now reflects `completion_state: incomplete` and the two `not_assessed` proof states.
- Contract release verification example is labeled `artifact_role: "untrusted_example"`, `release_verification_state: "fail"`, and `artifact_digest_status: "mismatch"`.
- Self-attestation case now expects `digest_verified: false` for current manifest reality.

## Slice 3: Source-Bound and External Trust Profiles

Purpose: separate local source-bound proof from external production trust.

Files:

- update `scripts/verify.sh`
- update `schema/contract-release-verification.schema.json`
- update `scripts/verify-self-attestation.sh`
- add negative fixtures under `examples/contract-foundation/`

Required failures:

- `production_release_verified.value: true` with missing external evidence
- `production_release_verified.value: true` with local profile
- `production_release_verified.value: true` with identity mismatch
- `production_release_verified.value: true` with transparency or audit evidence missing
- `trusted_contract_release: true` with any required production state not passing
- any required state without a machine-readable reason when it fails, is not assessed, or cannot verify

Review gate:

- no secondary field can carry production trust while `trusted_contract_release` is false.
- `verify:external-trust` fails when required external evidence is absent.
- baseline/source-bound profiles may report external evidence as `not_assessed` without claiming production trust.

Implementation state:

- `scripts/verify.sh --profile source-bound` emits `source_bound_local_release` proof summaries and fails when source-bound artifact proof is mismatched or the checkout is dirty.
- `scripts/verify.sh --profile external-trust` emits `external_production_trust` proof summaries and fails with explicit missing external attestation, identity, and transparency/audit states.
- `package.json` exposes `verify:source-bound` and `verify:external-trust`.

## Non-Goals After Trust Closure

- Block 06 real-run completion
- broad model/harness aggregation
- `sdp-gate` policy consumption

These are not allowed to hide a missing external trust check. They are outside Block 07 only after `verify:external-trust` has either passed for a real supported profile or kept Block 07 explicitly open.
