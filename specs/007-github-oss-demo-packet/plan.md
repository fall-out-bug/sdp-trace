## Summary

Create a reviewed plan for converting the existing demo direction into a
GitHub-first OSS demo of the Change Evidence Packet v0 product slice delivered
by 006.

The first buyer-facing demo should not be a local enterprise baseline. It should
be a GitHub PR with OSS agent/harness evidence and a packet a CTO can read.

The current demo repo is useful precisely because it is not sterile. It is not
yet the finished CTO packet demo, but it is the right default substrate for a v2
packetization track. The recommended path is to preserve current history as v1
observation evidence and continue in the same repository with packet artifacts,
GitHub PR binding, CI artifact binding, and explicit residual gaps.

## Sequencing Rule

006 must complete before 007 demo implementation starts. In this context,
"complete" means the product slice has reviewed schema, validator, renderer,
CLI validate/render behavior, and fixtures for happy path, missing
verification, expired artifact, contradiction, and `agent_claimed_verification`.

Every CTO-visible 007 demo packet must be tool-generated by the 006 renderer
and validated by the 006 validator.

`sdp-trace` recorder setup is outside the developer prompt. The OpenCode/GSD
feature prompt must be an ordinary implementation task and must not instruct
the route to use `sdp-trace`, maintain evidence, update trace files, or close
packet rows. Recorder friction, missing observation, and product gaps are
captured by `sdp-trace` or the packet as evidence states.

The trust scope is `local_observed` unless GitHub/CI, signed, externally
timestamped, or customer-equivalent evidence raises a specific row. Checked-in
recorder output is usable only when the demo regenerates or live-validates it,
or when GitHub/CI retained artifacts bind it by resolver and digest. Full
recorder passivity is not claimed from prompt discipline alone; prompt/setup
metadata can support `PC-AGENT-ROUTE: partial`, while `pass` requires stronger
machine evidence of the passivity boundary.

## Workstream A: Demo Repository V2

### A1: Preserve V1

Before v2 packetization work:

- tag current demo repo head as `demo-v1-observation`;
- record current repo URL, branch, head SHA, and known proof limitations;
- keep current observation ledger in `sdp-trace` as historical evidence.

### A2: Create V2 Packetization Track

Preferred path: same repository, same GitHub identity, new v2 milestone and
packetization PRs.

Optional path: fresh `demo-v2` root branch after tagging v1, if the current
`main` is too noisy for the first buyer rehearsal.

The v2 track starts by adding packet infrastructure around current history:

- `.sdp-trace/demo-profile.json`;
- PR template requiring packet link and bundle link.
- `docs/demo-tracker.md`;
- CI artifact upload for packet and bundle paths;
- one packet generated from a selected existing feature PR or feature history.

Do not rebuild feature behavior before the packet path exists.

### A3: Setup PR

Create one setup PR that only establishes:

- build/test command;
- GitHub Actions artifact upload;
- packet artifact directory convention;
- demo tracker.

No feature behavior should be mixed into the setup PR.

The setup PR does not prove a feature packet. It must prove artifact upload by
publishing a setup artifact that is explicitly marked `setup_only` and
`not_assessed` for product rows, or by running a packet validation command once
the renderer exists.

Codex may author setup-only infrastructure changes in this PR. It must not
include application feature behavior or feature fixes.

The setup-only boundary must be machine-checkable or independently reviewed.
Default file scope is `.github/`, `.sdp-trace/`, `docs/demo-tracker.md`,
`.gitignore`, `.ignore`, `.opencode/` recorder configuration, and packet/bundle
directory placeholders. Any application source, application test, or functional
build behavior change makes the PR not setup-only unless reviewed and recorded
as a separate feature-affecting change.

### A4: Five Feature PRs

For each feature:

1. open GitHub issue or issue-like task ref;
2. prepare or reinstall `sdp-trace` without mentioning recorder duties in the
   feature prompt;
3. run OpenCode/GSD + MiniMax under passive `sdp-trace` observation;
4. let OpenCode/GSD implement or repair the feature;
5. record any Codex review feedback as friction or review evidence, then
   redirect OpenCode/GSD when fixes are required;
6. do not patch feature behavior directly with Codex;
7. run or observe Bazel verification;
8. open PR;
9. CI uploads packet and evidence bundle;
10. add review evidence;
11. update demo tracker with packet row states.

If the recorder cannot capture enough route/provenance/evidence for a
CTO-visible packet, classify the blocker. P0 `sdp-trace` product blockers are
fixed before claiming feature proof. P1 and lower issues are recorded and may be
fixed after the current feature unless they prevent the packet from proving the
demo claim.

For the first happy-path CTO-visible packet, `PC-AGENT-ROUTE` must be `pass` or
`partial` with recorder-observed OpenCode/GSD/MiniMax evidence. A P0 blocker
that prevents route/provenance proof blocks feature proof until `sdp-trace` is
fixed and the route is rerun or otherwise observed with retained evidence.
`cannot_verify` is acceptable only for non-successful packets, non-blocking
rows, or P1 and lower issues that do not prevent the demo claim.

Existing or backfilled feature candidates require a route/provenance
contamination audit before they can be used as CTO-visible proof. If feature
behavior was implemented or repaired by Codex, the feature must be excluded from
OpenCode/GSD route proof or the affected rows must remain
`cannot_verify`/`partial` with an explicit residual gap.

Before buyer rehearsal, run a first-packet gate that checks the minimum bar from
`spec.md` and records the result in the demo tracker or packet evidence bundle.
The rehearsal is blocked if the first happy-path packet does not meet the bar.
Theater findings for the negative demo must be generated or validated by 006
tooling. If 006 only validates a supplied `agent_claimed_verification` finding
instead of detecting it automatically, the packet must name that limitation and
must not claim automated theater detection.

### A5: Negative Theater PR

Create one GitHub draft PR that intentionally lacks independent verification
binding while the agent claims verification. Retained fixtures may support
tests, but they are not the CTO-visible negative demo.

Expected packet:

- `PC-VERIFICATION`: `partial` or `cannot_verify`;
- `PC-THEATER`: `partial`;
- finding: `agent_claimed_verification`;
- merge/release decisions: not approved.

## Reset Decision

Use this decision rule:

| condition | decision |
| --- | --- |
| Need strongest product proof | Keep existing repo and packetize current history. |
| All existing features fail the first-packet selection rule and minimum bar | Tag v1, create fresh `demo-v2` root branch in same repo. |
| Need polished public sales demo | Start new repo v2 after product proof exists. |

Recommendation: existing repo v2 packetization. It keeps the real product
problem visible: `sdp-trace` must organize imperfect agent-delivery evidence
without hiding contamination, gaps, or missing PR lifecycle evidence.

## Review And Approval Checkpoints

Before implementation:

- this SpecKit package exists;
- Product Contract v0 is approved or explicitly accepted as the governing
  contract;
- the demo-track decision is approved;
- Socratic review checks product proof, demo contamination, GitHub-first scope,
  and theater semantics;
- critical/major review findings are fixed or explicitly deferred.

Before claiming demo success:

- at least one feature PR has a generated packet;
- all packet refs resolve or are `cannot_verify`;
- CI artifact retention is verified from GitHub, not local files only;
- review/merge/release gaps remain explicit;
- negative theater example exists and is understandable.
