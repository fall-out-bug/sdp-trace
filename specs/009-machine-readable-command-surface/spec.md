# Feature Specification: Machine-Readable Command Surface

**Feature Branch**: `009-machine-readable-command-surface`  
**Created**: 2026-05-13  
**Status**: Draft for PI review  
**Input**: PR #43 DX review found that `sdp-trace` has a large command surface documented in frozen prose, while agents and tools have no stable machine-readable command contract.

## Product Boundary

This slice makes the current CLI command surface discoverable and drift-resistant. It does not redesign the CLI, change command semantics, or introduce a new framework dependency.

Allowed:

- Go structs or JSON generated by Go code;
- docs generated or checked from the command registry;
- focused tests and CI checks.

Not allowed:

- Node.js, npm, JavaScript, TypeScript, or `.mjs` tooling;
- replacing existing commands as part of this slice;
- claiming that command metadata proves semantic correctness of each command.

## Problem Statement

The CLI currently exposes many command families, flags, profiles, and trust states. Humans can read `--help`, and `doccheck` compares the top-level command surface against docs, but programmatic consumers still need to parse prose or hardcoded help text.

This creates three risks:

- agents cannot reliably discover valid commands, profiles, and flags;
- `usageText`, command handlers, docs, and tests can drift independently;
- future UX features such as shell completion or generated docs lack a stable source.

## Core Claim

This slice may claim:

> `sdp-trace` exposes a machine-readable description of its supported command surface, and docs/help drift is checked against that description.

This slice must not claim:

- full semantic validation for all command combinations;
- shell completion support unless implemented and tested;
- compatibility guarantees for hidden or undocumented flags;
- external production trust.

## Required User Stories

### US-001 - Command Surface JSON (P0)

An agent can ask `sdp-trace` for a machine-readable command surface and receive command names, subcommands, required flags, optional flags, positional/rest behavior, profile values where known, and trust notes.

**Independent Test**: Running the new command or flag emits deterministic JSON that can be parsed by Go tests and `jq`.

### US-002 - Generated Or Checked Help (P0)

The human top-level help and agent/reviewer entrypoint docs cannot silently drift from the command registry.

**Independent Test**: A Go test or `tools/doccheck` extension fails if a command registered in code is missing from help/docs, or if docs list a command not present in the registry.

### US-003 - Profile And State Discovery (P1)

Known profile identifiers and result states are exposed without requiring agents to scrape prose.

**Independent Test**: The machine-readable output includes known assessment profiles, witness kinds, packet sources, and state vocabulary where those values are finite and current.

### US-004 - Backward-Compatible CLI Behavior (P0)

Existing command invocations, help text, and tests continue to work.

**Independent Test**: `go test -count=1 ./...`, `go run ./tools/doccheck`, and the existing `go run ./cmd/sdp-trace --help` command surface pass after implementation.

## Functional Requirements

- **FR-001**: The command surface must be represented by typed Go data, not by ad hoc Markdown parsing.
- **FR-002**: Machine-readable output must include a schema version.
- **FR-003**: Command metadata must distinguish required flags, optional flags, repeated flags, rest command payloads, and output paths.
- **FR-004**: The implementation must preserve current CLI behavior.
- **FR-005**: Docs must explain whether the JSON surface is stable, experimental, or internal-to-agent workflows.
- **FR-006**: Any command that cannot be fully modeled yet must be explicitly marked `not_assessed` or `partial` in metadata rather than omitted silently.

## Non-Functional Requirements

- Use only Go and existing repository tooling.
- Keep generated output deterministic.
- Keep the registry readable enough for code review.
- Do not introduce a large framework to solve metadata rendering.

## Acceptance Criteria

- `go test -count=1 ./...` passes.
- `go run ./tools/doccheck` passes and checks the new source of truth.
- JSON syntax validation covers any committed command-surface examples.
- PI review planes complete for code/correctness, DX/UX, and requirements-vs-implementation.

## PI Review Prompt

Review this spec for whether it gives future agents enough information to implement a machine-readable command surface without over-scoping into a CLI rewrite. Focus on:

- whether the command metadata scope is precise enough;
- whether docs/help drift will become machine-checkable;
- whether any trust or compatibility claim overreaches;
- whether the first slice can stay small and Go-only.
