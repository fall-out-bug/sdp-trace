# Feature Specification: Invisible Flight Recorder

**Feature Branch**: `008-invisible-flight-recorder`
**Created**: 2026-05-12
**Status**: Draft - requires multi-plane review before implementation
**Input**: Demo audit findings from the GitHub OSS packet demo.

## Product Boundary

`sdp-trace` must be usable as a passive delivery recorder. A developer route
must not need to know that `sdp-trace` exists, mention `sdp-trace` in its
prompt, write evidence files, update packet rows, or maintain provenance.

The product may expose setup, CI, and operator commands, but those commands
must run outside the developer prompt path. Evidence generated by operators,
reviewers, CI, or integrators must be labeled by actor and authority instead of
being presented as developer-route evidence.

## Problem Statement

The demo proved packet readability and gate behavior, but it also exposed a
contamination risk: Codex could still curate `.sdp-trace/*`, `.evidence/*`, and
PR witness comments after feature work. That is acceptable as integration
metadata only when labeled, but it is not clean flight-recorder proof.

Manual packet or evidence editing is a product defect for the demo adoption
path. The clean target is:

```text
normal feature prompt -> OpenCode/GSD developer route
external recorder -> observed run artifacts
CI packet builder -> packet/bundle artifacts
PR comment/check -> links to retained packet artifacts
```

The developer route receives normal feature instructions only. `sdp-trace`
records and packages from outside that route.

## Core Claim

This slice may claim:

> For the supported GitHub/OpenCode-GSD demo profile, `sdp-trace` can install a
> non-interfering observer contract and produce packet artifacts from retained
> recorder, GitHub PR, CI, artifact, and review evidence without requiring the
> developer prompt to mention `sdp-trace` or requiring a human to hand-edit
> `.sdp-trace` or `.evidence`.

This slice must not claim:

- signed or audit-grade recorder integrity;
- full non-interference proof beyond the observed contract;
- support for every harness or agent;
- semantic quality of the delivered feature;
- merge approval, release approval, compliance approval, or production trust.

## Required User Stories

### US-001 - Invisible Developer Prompt (P0)

An operator can run a supported OpenCode/GSD feature delivery while the
developer prompt contains no instruction to use `sdp-trace`, write evidence,
update provenance, or close packet rows.

**Independent Test**: Given the retained prompt text or digest metadata, the
recorder reports whether forbidden recorder-duty phrases were present. A clean
prompt can support route proof; a contaminated prompt must downgrade route
evidence and name the reason.

### US-002 - Recorder-Owned Evidence Lifecycle (P0)

`sdp-trace` creates recorder output as append-only run directories and emits a
manifest that binds files, digests, actor, source commit, and generation method.

**Independent Test**: A verifier can distinguish recorder-owned evidence from
operator-authored annotations and refuses to treat manually edited evidence as
developer-route proof.

### US-003 - CI-Owned Packet Generation (P0)

CI can generate Change Evidence Packet bundles and rendered packets from live PR
metadata, check state, artifact availability, recorder manifests, and retained
review evidence without checked-in packet edits.

**Independent Test**: A PR workflow uploads packet artifacts and a bundle whose
`PC-VERIFICATION` row references the exact CI run and retained artifacts. A
checked-in stale packet cannot override the CI-generated packet.

### US-004 - GitHub Source Discovery (P0)

The packet builder can discover PR URL, base/head SHA, changed files, checks,
artifact IDs, and review refs from GitHub context or explicitly supplied
GitHub API JSON without a curated `github-input.json`.

**Independent Test**: The builder produces the same required packet rows from
GitHub context JSON and refuses missing or contradictory PR/check/artifact data
with `cannot_verify`.

### US-005 - Integration Action Attribution (P1)

Rebase, cherry-pick, squash, packet regeneration, witness comments, and PR base
changes are recorded as integration/review actions, not developer feature
authorship.

**Independent Test**: A packet with integration actions still keeps
`PC-AGENT-ROUTE` tied to the OpenCode/GSD run and lists integration actions in
metadata or residual gaps without upgrading route proof.

### US-006 - DX/UX Command Clarity (P1)

The command surface makes the clean path obvious:

```text
sdp-trace recorder install ...
sdp-trace recorder run --profile <profile> -- <developer-command...>
sdp-trace packet build-pr --source github-actions --out <dir>
```

Manual `packet build-github --github-input` remains available as fixture or
backfill tooling, but docs mark it as lower-authority for live demos.

**Independent Test**: `docs/agent-entrypoint.md`, `docs/change-evidence-packet.md`,
and CLI help explain which command is authoritative for live demo proof and
which command is a backfill/fixture path.

## Observer Contract Boundaries

The invisible path has three separate actors:

- `developer_route`: OpenCode/GSD and the feature prompt. This actor must not
  receive recorder duties or packet-maintenance instructions.
- `recorder`: `sdp-trace` run capture, prompt-boundary classification, and
  recorder-owned manifests. This actor observes and writes recorder artifacts.
- `ci_packet_builder`: GitHub Actions or fixture-mode CI reconstruction that
  packages retained evidence into packet artifacts.

These actors may reference each other by immutable refs, but they must not
share write authority over the same proof object. If two actors claim the same
artifact, the builder must keep the lower-authority claim as integration or
operator metadata and leave route proof `cannot_verify` unless retained
external evidence resolves the conflict.

## Command Contract

The supported live-demo route is:

```text
sdp-trace recorder run --profile local_development_recorder -- <developer-command...>
sdp-trace packet build-pr --source github-actions --out <dir>
```

Fixture and offline test mode is:

```text
sdp-trace packet build-pr --source github-fixture \
  --github-event <event.json> \
  --checks-json <checks.json> \
  --artifacts-json <artifacts.json> \
  --route-manifest <route.json> \
  --out <dir>
```

`packet build-pr` must write `bundle.json`, `change-evidence-packet.md`, and a
machine-readable `build-pr-result.json`. It must not read checked-in packet
Markdown or bundle JSON as authority. Existing `packet build-github
--github-input` remains available only for fixture/backfill usage.

## Prompt Boundary Classification

Prompt-boundary evidence is classified as:

- `clean`: retained prompt text or approved digest metadata is present and no
  forbidden recorder-duty phrase is detected.
- `contaminated`: retained prompt text includes instructions for the developer
  route to use `sdp-trace`, write `.sdp-trace` or `.evidence`, maintain
  provenance, update packets/bundles, close gate rows, or claim verification
  status.
- `digest_only`: prompt text is unavailable, but retained metadata provides a
  digest, capture actor, capture time, and capture method. This can support
  `partial` route proof only.
- `missing`: neither prompt text nor sufficient digest metadata is available.
  Route proof is `cannot_verify`.

The classifier must return a verdict, a route-proof effect, and
machine-readable reasons. Classifier matching is a safety control, not semantic
quality proof; ambiguous or malformed prompt metadata must fail closed.

## Evidence Authority Metadata

Every recorder or packet artifact entry created by this slice must carry:

- `actor`: `developer_route`, `recorder`, `ci_packet_builder`, `operator`, or
  `integration`.
- `write_authority`: `route_observed`, `recorder_owned`, `ci_generated`,
  `operator_authored`, `integration_authored`, or `unknown`.
- `generated_by`: command or source system that produced the artifact.
- `source_commit_state`: `clean_immutable_commit`, `dirty_local_checkout`,
  `github_workflow_run`, `external_retained_artifact`, or `unknown`.
- `source_ref`: run id, artifact id, commit SHA, event path, or retained URL
  when available.

`operator_authored`, `integration_authored`, `dirty_local_checkout`, and
`unknown` entries cannot satisfy developer-route proof by themselves.

## Stale Packet Override Prevention

For the live CI path, generated packet artifacts have higher authority than any
checked-in packet Markdown or checked-in bundle JSON. A stale checked-in packet
may be referenced as historical context only if it is labeled
`operator_authored` or `integration_authored`; it must not make
`PC-VERIFICATION` pass.

## Functional Requirements

- **FR-001**: Supported developer prompts MUST NOT require `sdp-trace`,
  evidence, provenance, packet, bundle, trace, or gate instructions.
- **FR-002**: The recorder MUST record prompt boundary metadata outside the
  developer prompt path.
- **FR-003**: The verifier MUST classify prompt contamination as `fail` or
  `partial` for route proof, with a machine-readable reason.
- **FR-004**: Recorder-owned evidence MUST include manifest entries with file
  path, digest, actor, source commit state, generated-by command, and write
  authority.
- **FR-005**: Manually authored `.evidence` or `.sdp-trace` files MUST NOT
  satisfy `PC-AGENT-ROUTE` or `PC-VERIFICATION: pass` unless they are explicitly
  marked as operator/integration evidence and backed by retained external refs.
- **FR-006**: CI-owned packet generation MUST produce both bundle JSON and
  rendered Markdown as uploaded artifacts.
- **FR-007**: CI-owned packet generation MUST bind `PC-VERIFICATION` to the
  current workflow run and retained artifact IDs.
- **FR-008**: GitHub source discovery MUST support GitHub Actions environment
  variables and supplied GitHub API JSON fixtures for offline tests.
- **FR-009**: The builder MUST fail closed as `cannot_verify` when PR, check,
  artifact, route, or prompt-boundary evidence is missing or contradictory.
- **FR-010**: Integration actions MUST be represented separately from developer
  route evidence.
- **FR-011**: Docs and `--help` MUST describe the invisible flow and mark
  manual packet input as backfill/fixture authority.
- **FR-012**: Release binary documentation and workflow MUST include any new
  command surface added by this slice.
- **FR-013**: Prompt-boundary tests MUST cover clean, contaminated,
  digest-only, missing, and malformed metadata cases.
- **FR-014**: `packet build-pr` MUST emit bundle JSON, rendered Markdown, and a
  result summary, and tests MUST prove all three outputs are produced.
- **FR-015**: `packet build-pr` MUST bind `PC-VERIFICATION` to the current
  workflow run id and retained artifact ids in GitHub Actions mode, or to
  fixture ids in offline tests.
- **FR-016**: GitHub API token values, authorization headers, and secrets MUST
  never be written to generated packet artifacts, result summaries, logs, or
  diagnostics.
- **FR-017**: CLI diagnostics for `cannot_verify` MUST name the missing or
  contradictory evidence class without implying a green gate.

## Acceptance Gates

1. Spec review: 3-5 independent review planes covering requirements,
   evidence/trust, security/non-interference, DX/UX, and implementation risk.
2. Implementation tests:
   - focused Go unit tests for prompt boundary classification;
   - packet builder tests using GitHub context/API JSON fixtures;
   - evidence manifest authority tests;
   - CLI tests for new command help and failure modes.
3. Regression tests:
   - `go test ./... -count=1`;
   - `jq empty schema/*.json` and changed examples;
   - `git diff --check`;
   - release binary build and checksum verification.
4. Review after implementation:
   - code plane;
   - evidence/trust plane;
   - DX/UX documentation plane.
5. PR:
   - branch PR to `main`;
   - CI green;
   - review findings recorded;
   - no direct commits to `main`.

## Out Of Scope

- General support for all agent harnesses.
- Signed transparency or customer PKI proof.
- Full semantic correctness assessment.
- Replacing GitHub Actions with another CI provider in this slice.
- Teaching the developer route to operate `sdp-trace`.
